iakaframe — l'équipe augmentée, cadrée

iakaframe n'est pas une technologie, c'est une discipline de travail : des rôles fermés, des instructions écrites avant le code, un humain qui décide à chaque jalon. Le modèle, le runner ? Un substrat interchangeable. La qualité n'est pas dans l'outil — elle est dans la méthode.

v0.4.0 · 2026-07-05 · document de référence
Comprendre

L'idée : un décideur, une équipe d'experts

iakaframe transforme « une IA qui code » en une équipe qui livre. Le principe tient en une phrase : c'est le workflow qui produit la qualité, pas l'IA. L'IA amplifie ; le workflow cadre.

Une discipline, pas une technologie

iakaframe n'est pas une technologie, c'est une discipline de travail — un protocole de rôles, de gestes et de jalons. L'IA (le modèle, le runner, l'outil agentique) n'est qu'un substrat interchangeable : ce qui produit la qualité, c'est la méthode, pas l'outil. On peut changer de modèle, de runner, d'outil — la discipline, elle, reste. C'est ce qui la rend transmissible (les kits) et durable.

Le décideur, c'est l'utilisateur

Le décideur n'est pas un persona : c'est l'humain, l'utilisateur. Il est au-dessus de l'équipe et ne délègue jamais la réflexion — seulement l'exécution.

  • Il porte la vision et tranche l'architecture.
  • Il valide ou corrige, teste le résultat dans l'app réelle.
  • Il tranche les jalons humains (validation d'une instruction, feu vert de mise en production).

Une équipe d'experts spécialisés

Sous le décideur, la réflexion et l'exécution sont distribuées sur une équipe d'experts — des rôles spécialisés, aux périmètres étanches, sans le moindre chevauchement. Chacun a ses droits, ses garde-fous, ses entrées et ses sorties. On sait toujours qui parle et depuis quelle phase. Chaque rôle est joué par un persona : le rôle est la fonction (cadrage, développement, qualité, coordination…), le persona en est l'incarnation jouable, portable d'un runner à l'autre.

Info : le nombre d'experts n'est pas figé — l'équipe se compose selon le besoin. Ce qui est invariant, c'est la règle : un rôle = un périmètre fermé, zéro chevauchement.

Un rôle = un contrat packagé

Chaque rôle borne ses permissions (outils autorisés), ses interdits (ce qu'il ne fait pas) et son process (entrée → sortie → jalon). Lisible, réutilisable d'un projet à l'autre.

La coordination à deux niveaux

La coordination existe à deux étages : une coordination de portefeuille (au-dessus des projets : oriente, répartit entre projets, commande les coordinations de projet) et, dans chaque projet, une coordination de projet qui répartit le travail entre les experts et surveille les jalons.

Info : les rôles sont incarnés (un nom de code interne, une couleur) pour être mémorisables. Dans toute documentation externe — comme cette page — on ne désigne jamais un rôle par son nom de code : voir l'onglet Les rôles.

Comprendre

La douleur d'origine : l'IA qui code sans cadre

Une IA sans cadre génère du code plausible — pas forcément du logiciel fiable. Elle est un exécutant puissant mais aveugle : elle ne sait pas ce qu'elle ne sait pas. Livrée à elle-même, elle produit quatre douleurs concrètes.

1 · La dérive de périmètre

« Tant qu'on y est… » — l'IA ajoute des fonctions non demandées, optimise localement et perd de vue l'architecture globale. Vécu : vouloir embarquer FFmpeg pour transcoder une vidéo alors que les players natifs décodent déjà tout en matériel. Solution complexe, inutile.

2 · L'IA qui valide son propre travail

Quand celui qui code juge aussi sa propre qualité, il devient juge et partie. Le code « compile » et est déclaré « prêt » — sans regard indépendant. C'est l'anti-patron le plus coûteux.

3 · La perte de traçabilité

La mémoire d'une IA est volatile. Sans trace écrite, les décisions techniques s'évaporent d'une session à l'autre : six mois plus tard, personne ne sait pourquoi ce choix a été fait.

4 · L'absence de méthode reproductible

Chaque tâche repart d'un prompt vague suivi d'une acceptation aveugle. Rien ne se capitalise : ni les préférences, ni les corrections, ni le cadre. Le « vibe coding » ne passe pas à l'échelle.

Attention : le problème n'est pas la puissance du modèle — c'est l'absence de cadre autour. Un modèle plus fort sans méthode dérive simplement plus vite.

Ce que la méthode refuse d'être

  • Pas du « vibe coding » — chaque ligne est spécifiée, vérifiée par des outils, validée par un humain.
  • Pas de l'automatisation aveugle — l'IA ne tourne pas en boucle ; le feedback humain est structurel, pas optionnel.
  • Pas un remplacement du développeur — il fait moins de frappe et plus de décisions ; son métier monte en abstraction.
Comprendre

La méthode : un cycle, des jalons, une trace

Le besoin ne descend jamais directement dans le code. Il passe par un cycle où chaque étape ferme un peu plus l'ambiguïté, jusqu'à une instruction écrite et vérifiable — puis l'exécution. Trois jalons rythment les 3 phases ; un quatrième garde la porte de la production.

Le cycle d'une feature, et où se posent les jalons

  1. Besoin — le décideur exprime ce qu'il veut.
  2. Analyse — lecture seule de l'existant (code, conventions, état des lieux).
  3. Discussion — arbitrages, options, périmètre ; on pose le problème avant la solution.
  4. Instruction écrite — le besoin devient un fichier fermé dans specs/instructions/.
  5. Validation — jalon humain le décideur valide (ou corrige) l'instruction. Ferme la P1.
  6. Implémentation — le code s'écrit par petits pas, en commits atomiques.
  7. Test & feedback — jalon auto verdict qualité PASS, puis le décideur teste dans l'app réelle. Ferme la P2 (puis la P3 au stage).
  8. Boucle — une correction remonte au niveau de la décision, pas du micro-management ligne à ligne.

Astuce : quand l'IA prend une mauvaise direction, on ne la corrige pas ligne par ligne. On remonte à la décision, et la décision redescend sous forme d'instruction corrective écrite.

Les 3 phases + le squad prod, fermées par leurs jalons

La chaîne de dev a pour cible le staging et avance en trois phases ; chaque phase est fermée par un jalon. La production est un squad séparé, gardé par un jalon humain.

Le graphe des délégations : une conversation-arbre

Une conversation iakaframe n'est pas une liste : c'est un arbre (uuid → parentUuid). Le tronc « main » porte le fil principal ; une délégation ouvre une sidechain. Sur chaque nœud, le badge est l'attribution machine (attributionAgent) rendue visible — il est émis, pas décoré.

La position de la pastille porte le sens

Quand un rôle s'adresse au décideur, il s'identifie par un badge <pastille> [ROYAUME][Rôle]. Ce n'est pas un mot-clé qui marque l'ouverture ou la clôture, mais la position de la pastille :

// ouverture — pastille AVANT le bloc
🟠 [ROYAUME][coordinateur] — je délègue le cadrage à l'architecte-cadreur…

// clôture — pastille APRÈS le bloc
…instruction transmise. [ROYAUME][coordinateur] 🟠

Les mots « START » / « STOP » sont bannis : ils feraient double emploi avec la position.

On n'écrit jamais le badge d'un rôle pour lui faire dire des mots qu'il n'a pas produits.

Comprendre

L'agnosticisme : un cadre de rôles, pas un outil

iakaframe est volontairement agnostique du stack. Elle ne dépend d'aucun langage, framework, LLM ou hébergeur particulier : c'est un cadre de rôles et de gestes, transposable ailleurs. Les rôles priment sur l'implémentation.

Le fil directeur : une discipline se transpose, une technologie se périme. iakaframe est du premier genre — un protocole de rôles, de gestes et de jalons. Change le modèle, le runner ou l'outil agentique : la discipline reste. C'est précisément ce qui la rend portable (les kits) et durable.

Le geste prime sur l'outil

Chaque brique d'outillage nomme un geste (commit, mémoire humaine, support visuel…) et une implémentation courante. L'implémentation est un choix par défaut, pas une dépendance : le nom d'un outil ou d'une marque ne doit jamais tenir lieu d'identité au geste.

Self-hosted d'abord, mais réimplantable

La méthode privilégie le self-hosted / open-source : pour tout choix de backend, la version locale est l'option n°1, le cloud n'est qu'un repli justifié. Mais ce n'est qu'un défaut de goût, pas une dépendance : les mêmes rôles se rejouent avec d'autres briques. Les définitions de rôles sont pensées pour se décliner sur plusieurs incarnations d'IA — aujourd'hui l'implémentation courante, demain d'autres.

Une équipe, des runners hétérogènes

Un rôle est un contrat portable (identité + périmètre + geste) ; le runner n'est que le substrat d'exécution. L'équipe peut donc être hétérogène : chaque rôle peut être issu et exécuté sur un runner différent, chacun avec son propre modèle.

Astuce : la bonne question n'est jamais « quel outil ? » mais « quel geste ce rôle sert-il, et son jalon est-il franchi ? ». Change l'outil, garde le geste : la méthode tient toujours.

Comprendre

L'emboîtement : le contexte est empilé, du grain à l'enveloppe

Le comportement effectif d'un persona, à tout instant, est la somme empilée de plusieurs couches d'instructions. Chaque couche externe englobe et complète les internes — rien n'est isolé, tout s'additionne.

1 · Les contextes emboîtés

Premier emboîtement, structurel : le portefeuille contient les projets, chaque projet a son équipe d'experts, chaque expert est techniquement incarné.

Portefeuille — ~/work

La coordination de portefeuille : oriente entre projets, ne fait pas le métier.

Projet — un dépôt

Sa coordination de projet, son fichier d'instructions (CLAUDE.md pour Claude Code, AGENTS.md ailleurs), ses specs/, sa stack Docker.

Équipe — les rôles d'experts

Un périmètre fermé par rôle, une phase, un jalon.

Incarnation — persona + skill(s)

Le persona = le contrat (incarné en subagent sur Claude Code, en profil/Model ailleurs) ; la skill = la méthode (le geste outillé).

2 · L'inclusion du contexte, en 5 couches d'instructions

Second emboîtement, celui qui compte vraiment : des instructions, pas seulement des dossiers. De l'enveloppe (la méthode, au-dessus de tout) vers le grain (les interdits d'un rôle), chaque couche est un fichier réel.

5 · portefeuille.md — la méthode, au-dessus de tous les projets

Le fichier d'instructions global, lu dans toutes les sessions, au-dessus de tous les projets. Implémentation courante : ~/.claude/CLAUDE.md (Claude Code) — AGENTS.md pour d'autres outils. « portefeuille.md » nomme le rôle, pas un fichier littéral.

4 · projet.md — les règles & l'assemblage du projet

Le fichier d'instructions du projet + specs/PROJET.md — assemble les experts et les conventions du projet. Implémentation courante : <projet>/CLAUDE.md (Claude Code) ou AGENTS.md (Codex, Ollama, OpenWebUI…).

3 · persona — le contrat de rôle

agents/<rôle>.md — identité + périmètre + tools + skills portées.

2 · skills — un geste outillé

Les SKILL.md — source dans le dossier skills/ du dépôt, déployées dans le dossier de skills de l'outil (~/.claude/skills/ pour Claude Code).

1 · tools / règles / interdits — le grain

Le frontmatter tools: du contrat + le périmètre « ne sort jamais de… » (interdits) + les garde-fous par hooks (identité, gestes, périmètre).

Info — la somme empilée : à tout instant, comportement effectif = portefeuille.md ⊃ projet.md ⊃ persona ⊃ skills ⊃ tools/règles/interdits. Un persona n'agit jamais « nu » : il agit avec la méthode globale, plus les règles de son projet, plus son contrat, plus ses gestes, plus ses garde-fous — tout empilé.

Le contrat et la méthode

Chaque rôle est incarné par un persona défini dans un contrat (agents/<rôle>.md) : il s'exécute en contexte isolé — un subagent sur Claude Code, un profil ou un Model ailleurs — avec ses outils propres (frontmatter tools:), parallélisable. Son savoir-faire vit dans une ou plusieurs skills (skills/iakaframe-*). Le persona est le contrat ; la skill est la méthode.

Source d'image et copie active

Les skills et contrats vivent à la source dans le dépôt (agents/*, skills/iakaframe-*) — l'image — et sont déployés dans le dossier actif de l'outil (~/.claude/ pour Claude Code) — la copie chargée à l'exécution. Règle d'or : on édite la source, puis on redéploie ; jamais la copie à la main.

Info : déployer une équipe sur un projet copie les contrats + leurs skills dans le dossier de config de l'outil du projet (<projet>/.claude/ pour Claude Code) — et le catalogue de chartes pour le studio design. Une équipe déployée mais pas encore lancée, dans le lexique maison : « la compagnie est à l'auberge ».

L'outillage de la méthode

La méthode s'exécute à travers un outillage concret. On le classe par geste — ce qu'il sert — l'outil n'étant que l'implémentation courante, cohérente avec l'agnosticisme du cadre.

Les skills de portefeuille, de coordination et de rédaction portent en interne le nom de code de leur rôle ; elles sont désignées ici par leur geste, conformément à la règle de terminologie externe.

Autour des skills

Le CLI multi-plateforme

Le paquet @naonedge/iakaframe (Node, zéro dépendance) porte les commandes de la méthode : banner, brief, jalon, snapshot, update, onboard, recap… C'est la voie cross-OS ; les scripts .ps1 restent le chemin rapide sous Windows.

Commit / versionnement

Geste par défaut : une forge self-hosted, Forgejo, en HTTP + token — cohérent avec le « self-hosted d'abord ». Réimplantable sur GitHub, GitLab ou toute forge. Le token n'est jamais écrit en dur ni commité.

Les scripts de cycle

onboard amorce (structure + dépôt + premier état des lieux). snapshot régénère l'état des lieux (faits git + récit). update scelle un checkpoint (état des lieux + commit global + push). Init et update s'auto-détectent.

La mémoire humaine

Miroir humain de l'état des lieux, hors du dépôt : les docs structurants publiés dans une base de notes auto-hébergée (AppFlowy par défaut), lisibles sans cloner ni lire du Markdown brut. Alimentée par instrumentation, pas à la main.

Le canal d'identité (badges & pastilles)

Quand un rôle s'adresse au décideur, il s'identifie : <pastille> [ROYAUME][Rôle]. La position de la pastille porte le sens — avant le bloc = ouverture, après = clôture. La couleur = la phase servie, partagée entre rôles.

Les hooks garde-fous

Des hooks tiennent la discipline sans la déléguer au modèle : garde d'identité (double badge), garde du canal des gestes (délégation auditée, hors-roster bloqué), garde de périmètre (un geste hors du projet est signalé/bloqué). Bornés, jamais utilisés pour déclencher le bootstrap.

La stack Docker isolée

Chaque projet tourne dans sa stack : réseau, volumes et conteneurs préfixés par projet, ports hôte distincts. Jamais de partage de ressources entre projets de la famille.

Les kits d'incarnation

Des kits prêts à poser pour incarner la méthode sur plusieurs outils : kit-claude, kit-codex, kit-openwebui, kit-anythingllm, kit-ollama. La même méthode, plusieurs incarnations d'IA.

Le principe des kits : une méthode, N incarnations

Un kit est une incarnation de la même méthode sur une solution donnée. La méthode — les rôles, les 3 phases, le cadrage-avant-code, le rituel d'identité — est identique d'un kit à l'autre. Ce qui change, c'est le support d'incarnation : la solution, le fichier d'instructions du contrat, et la forme que prend le roster (subagents natifs sur Claude Code, personas de manière générale, ou Models importables).
