Méthode · document chapeau

iakaframe — l'équipe augmentée, cadrée

Une méthode de travail avec l'IA : des rôles fermés, des instructions écrites avant le code, et un humain qui décide à chaque jalon. La qualité n'est pas dans le modèle — elle est dans la méthode.

v0.2.0 · 2026-07-05 · document de référence
Comprendre

L'idée : une équipe, pas un prompt

iakaframe transforme « une IA qui code » en une équipe qui livre. Le principe tient en une phrase : c'est le workflow qui produit la qualité, pas l'IA. L'IA amplifie ; le workflow cadre.

Trois acteurs, zéro chevauchement

À la base, un modèle conceptuel simple — trois responsabilités qui ne se recouvrent jamais :

  • Le décideur (l'humain) — porte la vision, tranche l'architecture, teste le résultat réel, valide à chaque jalon. Il délègue l'exécution, jamais la réflexion.
  • La réflexion / le cadrage — analyse l'existant en lecture seule et transforme un besoin en instruction écrite ; ne touche jamais au code de production.
  • L'exécution — lit l'instruction validée, code, build, teste, commite.

Cette séparation est le cœur : le jour où celui qui réfléchit est aussi celui qui exécute sans garde-fou, il n'y a plus de contrôle.

De trois acteurs à une compagnie

Pour industrialiser le développement au fil de l'eau, les couches réflexion et exécution se spécialisent en une équipe d'agents, chacun avec un rôle fermé : ses droits, ses garde-fous, ses entrées et sorties. On sait toujours qui parle et depuis quelle phase.

Un rôle = un contrat packagé

Chaque rôle borne ses permissions (outils autorisés), ses interdits (ce qu'il ne fait pas) et son process (entrée → sortie → jalon). Lisible, réutilisable d'un projet à l'autre.

Deux niveaux d'orchestration

Un niveau portefeuille ouvre la bonne porte entre projets ; à l'intérieur d'un projet, un coordinateur répartit le travail entre les rôles et surveille les jalons.

Info : les rôles sont incarnés (un nom de code interne, une couleur) pour être mémorisables. Dans toute documentation externe — comme cette page — on ne désigne jamais un rôle par son nom de code : voir l'onglet Les rôles.

Comprendre

La douleur d'origine : l'IA qui code sans cadre

Une IA sans cadre génère du code plausible — pas forcément du logiciel fiable. Elle est un exécutant puissant mais aveugle : elle ne sait pas ce qu'elle ne sait pas. Livrée à elle-même, elle produit quatre douleurs concrètes.

1 · La dérive de périmètre

« Tant qu'on y est… » — l'IA ajoute des fonctions non demandées, optimise localement et perd de vue l'architecture globale. Vécu : vouloir embarquer FFmpeg pour transcoder une vidéo alors que les players natifs décodent déjà tout en matériel. Solution complexe, inutile.

2 · L'IA qui valide son propre travail

Quand celui qui code juge aussi sa propre qualité, il devient juge et partie. Le code « compile » et est déclaré « prêt » — sans regard indépendant. C'est l'anti-patron le plus coûteux.

3 · La perte de traçabilité

La mémoire d'une IA est volatile. Sans trace écrite, les décisions techniques s'évaporent d'une session à l'autre : six mois plus tard, personne ne sait pourquoi ce choix a été fait.

4 · L'absence de méthode reproductible

Chaque tâche repart d'un prompt vague suivi d'une acceptation aveugle. Rien ne se capitalise : ni les préférences, ni les corrections, ni le cadre. Le « vibe coding » ne passe pas à l'échelle.

Attention : le problème n'est pas la puissance du modèle — c'est l'absence de cadre autour. Un modèle plus fort sans méthode dérive simplement plus vite.

Ce que la méthode refuse d'être

  • Pas du « vibe coding » — chaque ligne est spécifiée, vérifiée par des outils, validée par un humain.
  • Pas de l'automatisation aveugle — l'IA ne tourne pas en boucle ; le feedback humain est structurel, pas optionnel.
  • Pas un remplacement du développeur — il fait moins de frappe et plus de décisions ; son métier monte en abstraction.
Comprendre

La méthode : un cycle, des jalons, une trace

Le besoin ne descend jamais directement dans le code. Il passe par un cycle où chaque étape ferme un peu plus l'ambiguïté, jusqu'à une instruction écrite et vérifiable — puis l'exécution.

Le cycle d'une feature

  1. Besoin — le décideur exprime ce qu'il veut.
  2. Analyse — lecture seule de l'existant (code, conventions, état des lieux).
  3. Discussion — arbitrages, options, périmètre ; on pose le problème avant la solution.
  4. Instruction écrite — le besoin devient un fichier fermé dans specs/instructions/.
  5. Validation — le décideur valide (ou corrige) l'instruction. Jalon humain.
  6. Implémentation — le code s'écrit par petits pas, en commits atomiques.
  7. Test & feedback — l'humain teste dans l'app réelle ; le feedback est mémorisé.
  8. Boucle — une correction remonte au niveau de la décision, pas du micro-management ligne à ligne.

Astuce : quand l'IA prend une mauvaise direction, on ne la corrige pas ligne par ligne. On remonte à la décision, et la décision redescend sous forme d'instruction corrective écrite.

Les 3 phases (cible staging) + le squad prod

La chaîne de dev a pour cible le staging et avance en trois phases. À chaque phase, un rôle est aux commandes ; le coordinateur vérifie le jalon avant de passer à la suivante.

PhaseRôle aux commandesEntrée → sortieJalon
🔵 P1 — Cadrage l'architecte-cadreur besoin → specs/instructions/{feature}.md humain
🔴 P2 — Réalisation le développeur (×N) + le responsable qualité instruction → branche + commits + verdict PASS auto
🟢 P3 — Déploiement staging le développeur (devops) + le responsable qualité PASS → build en staging vX.Y.Z-rc auto
La chaîne s'arrête au staging — la prod est un squad séparé

🟣 Surveillance l'équipe de déploiement production prod → santé OK / alerte / rollback continu

Frontière nette : dev → staging (les 3 phases), puis prod (squad séparé), avec une couture humaine entre les deux.

La position de la pastille porte le sens

Quand un rôle s'adresse au décideur, il s'identifie par un badge <pastille> [ROYAUME][Rôle]. Ce n'est pas un mot-clé qui marque l'ouverture ou la clôture, mais la position de la pastille :

// ouverture — pastille AVANT le bloc
🟠 [ROYAUME][coordinateur] — je délègue le cadrage à l'architecte-cadreur…

// clôture — pastille APRÈS le bloc
…instruction transmise. [ROYAUME][coordinateur] 🟠

Les mots « START » / « STOP » sont bannis : ils feraient double emploi avec la position.

Anatomie d'une délégation A → B (sans vol de badge)

Une délégation produit une chaîne de badges ininterrompue. L'orchestrateur ne parle jamais dans sa voix entre l'ouverture et la clôture du rôle délégué, et il ne restitue jamais le travail d'un autre à la première personne.

  1. A ouvre (pastille avant) et annonce qu'il délègue à B.
  2. A clôt (pastille après).
  3. B ouvre (pastille avant) et parle à la première personne.
  4. B travaille, puis restitue son résultat.
  5. B clôt (pastille après).
  6. A rouvre pour restituer en relais — sous le badge de B, cité verbatim — puis commente sous son propre badge.
🔴 [ROYAUME][développeur] — restitué par le coordinateur

{le message du rôle délégué, cité tel quel, jamais reformulé en « je »}

Attention — anti-ventriloquie : un badge n'introduit que les mots propres du rôle qu'il nomme. Toute reformulation ou synthèse est la voix de l'orchestrateur et passe sous son propre badge. On n'écrit jamais le badge d'un rôle pour lui faire dire des mots qu'il n'a pas produits.

Les jalons (gates)

Un jalon est un point de contrôle rendu très visible : instruction prête, dev à vérifier, verdict qualité, feu vert prod. Il s'affiche en trois zones — qui pose, quoi, qui valide — puis, à la validation, le récepteur annonce « JALON VALIDÉ » et explique la suite.

ZoneRôleExemple
Émetteurqui pose le jalonl'architecte-cadreur pose l'instruction cadrée
Contenuce qui est soumisl'instruction + les fichiers à vérifier en chemin:ligne
Récepteurqui validele décideur (souvent), ou le rôle suivant

Jalons humains — non automatisables

La validation d'une instruction (P1) et la bascule en production sont des décisions humaines, toujours. Sans feu vert explicite et tracé, la chaîne s'arrête et attend.

Jalons automatiques — les tests suffisent

Le passage dev → staging repose sur un verdict qualité PASS indépendant (tests verts, lint, typage). Pas besoin d'humain : les outils tranchent.

À l'entrée du jalon de dev, l'instruction validée est accompagnée d'une estimation chiffrée (jour-homme, complexité, inconnues) pour que le décideur engage en connaissance de cause.

Comprendre

L'agnosticisme : un cadre de rôles, pas un outil

iakaframe est volontairement agnostique du stack. Elle ne dépend d'aucun langage, framework, LLM ou hébergeur particulier : c'est un cadre de rôles et de gestes, transposable ailleurs. Les rôles priment sur l'implémentation.

Ce qui est stable vs ce qui est interchangeable

Invariant (le cadre)Interchangeable (l'implémentation)
Séparer réflexion et exécutionLe modèle qui réfléchit / qui code
Instruction écrite avant le codeLe format d'édition, l'IDE, le CLI
Gate qualité indépendantLes outils (tsc, ESLint, pytest, clippy…)
Jalons humains tracésLe canal (terminal, Slack, Mattermost)
Trace durable des décisionsLe support (git, forge auto-hébergée, wiki)
Isolation par projetLa techno de conteneur / d'environnement

Le geste prime sur l'outil

Chaque brique d'outillage nomme un geste (commit, mémoire humaine, support visuel…) et une implémentation courante. L'implémentation est un choix par défaut, pas une dépendance : le nom d'un outil ou d'une marque ne doit jamais tenir lieu d'identité au geste.

GesteImplémentation courante (défaut)Réimplantable en
Commit / versionnementforge self-hosted (Forgejo)GitHub, GitLab…
Mémoire humaineAppFlowy auto-hébergétout wiki / base de notes

Self-hosted d'abord, mais réimplantable

La méthode privilégie le self-hosted / open-source : pour tout choix de backend, la version locale est l'option n°1, le cloud n'est qu'un repli justifié. Mais ce n'est qu'un défaut de goût, pas une dépendance : les mêmes rôles se rejouent avec d'autres briques. Les définitions de rôles sont pensées pour se décliner sur plusieurs incarnations d'IA — aujourd'hui l'implémentation courante, demain d'autres.

Astuce : la bonne question n'est jamais « quel outil ? » mais « quel geste ce rôle sert-il, et son jalon est-il franchi ? ». Change l'outil, garde le geste : la méthode tient toujours.

Comprendre

L'emboîtement : portefeuille ⊃ projets ⊃ rôles ⊃ skills

La méthode est une suite de poupées gigognes. Chaque niveau contient le suivant, sans jamais mélanger les contextes. C'est cette imbrication qui rend l'ensemble étanche et réutilisable.

Portefeuille — ~/work

Un seul niveau au-dessus de tout : oriente entre projets, ne fait pas le métier.

Projet — un dépôt

Sa propre équipe, son CLAUDE.md, ses specs/, sa stack Docker.

Rôle — un agent de l'équipe

Un périmètre fermé, une phase, un jalon.

Incarnation — subagent + skill(s)

Le subagent = le contrat (contexte isolé, outils propres, dispatchable). La skill = la méthode (le geste outillé, réutilisable).

Le contrat et la méthode

Chaque rôle est un subagent (fichier agents/<rôle>.md) : contexte isolé, outils propres, parallélisable (plusieurs développeurs en worktrees). Son savoir-faire vit dans une ou plusieurs skills (skills/iakaframe-*) qu'il charge. Le subagent est le contrat ; la skill est la méthode.

Source d'image et copie active

Les skills et contrats vivent à la source dans le dépôt (agents/*, skills/iakaframe-*) — c'est l'image — et sont déployés dans ~/.claude/ (la copie active chargée à l'exécution). Règle d'or : on édite la source, puis on redéploie ; jamais la copie à la main.

Une skill = un geste outillé, réutilisable

Une skill n'est pas liée à un projet : c'est un geste défini une fois (cadrer, tester, versionner, mémoriser…) et rejoué partout. Un projet reçoit sa copie scopée de l'équipe et des skills ; deux projets ne partagent jamais un contexte. La définition est mutualisée, l'exécution est étanche.

Info : déployer une équipe sur un projet copie les contrats + leurs skills dans <projet>/.claude/ (et le catalogue de chartes pour le studio design). Une équipe déployée mais pas encore lancée, dans le lexique maison : « la compagnie est à l'auberge ».

Les skills de portefeuille, de coordination et de rédaction portent en interne le nom de code de leur rôle ; elles sont désignées ici par leur geste, conformément à la règle de terminologie externe.

Autour des skills

Le CLI multi-plateforme

Le paquet @naonedge/iakaframe (Node, zéro dépendance) porte les commandes de la méthode : banner, brief, jalon, snapshot, update, onboard, recap… C'est la voie cross-OS ; les scripts .ps1 restent le chemin rapide sous Windows.

Commit / versionnement

Geste par défaut : une forge self-hosted, Forgejo, en HTTP + token — cohérent avec le « self-hosted d'abord ». Réimplantable sur GitHub, GitLab ou toute forge. Le token n'est jamais écrit en dur ni commité.

Les scripts de cycle

onboard amorce (structure + dépôt + premier état des lieux). snapshot régénère l'état des lieux (faits git + récit). update scelle un checkpoint (état des lieux + commit global + push). Init et update s'auto-détectent.

La mémoire humaine

Miroir humain de l'état des lieux, hors du dépôt : les docs structurants publiés dans une base de notes auto-hébergée (AppFlowy par défaut), lisibles sans cloner ni lire du Markdown brut. Alimentée par instrumentation, pas à la main.

Le canal d'identité (badges & pastilles)

Quand un rôle s'adresse au décideur, il s'identifie : <pastille> [ROYAUME][Rôle]. La position de la pastille porte le sens — avant le bloc = ouverture, après = clôture. La couleur = la phase servie, partagée entre rôles.

Les hooks garde-fous

Des hooks tiennent la discipline sans la déléguer au modèle : garde d'identité (double badge), garde du canal des gestes (délégation auditée, hors-roster bloqué), garde de périmètre (un geste hors du projet est signalé/bloqué). Bornés, jamais utilisés pour déclencher le bootstrap.

La stack Docker isolée

Chaque projet tourne dans sa stack : réseau, volumes et conteneurs préfixés par projet, ports hôte distincts. Jamais de partage de ressources entre projets de la famille.

Les kits d'incarnation

Des kits prêts à poser pour incarner la méthode sur plusieurs outils : kit-claude, kit-codex, kit-openwebui, kit-anythingllm, kit-ollama. La même méthode, plusieurs incarnations d'IA.
