iakaframe : l'équipe de dev augmentée

Un développeur, deux IA aux rôles séparés et une infra auto-hébergée — la méthode qui produit du logiciel fiable aujourd'hui, et trace la route vers un écosystème d'agents CI/CD demain.

v3 · 2026-06-14 · interne · méthode + infra + équipe d'agents
Principe fondateur

C'est le workflow qui produit la qualité, pas l'IA

Une IA sans cadre génère du code plausible. Un workflow structuré — rôles clairs, instructions écrites, outils de vérification — produit du logiciel fiable. La différence entre les deux, c'est la méthode.

Le postulat est simple : l'IA est un exécutant puissant mais aveugle. Elle ne sait pas ce qu'elle ne sait pas. C'est le développeur qui apporte la vision, les décisions d'architecture et les critères de qualité.

L'IA amplifie ; le workflow cadre.

iakaframe est la méthode de collaboration IA-augmentée extraite et généralisée des projets IAKA Vod, robotimmo, iakaAFstorage, iakabox et iakaJarvis. Elle est volontairement agnostique du stack : elle s'applique à n'importe quel langage, framework ou type de projet.

Aujourd'hui

Une équipe de dev augmentée : un humain + deux IA aux rôles séparés, cadrés par des fichiers d'instructions.

L'infra

Un homelab auto-hébergé (iakabox) : Git, IA locale, reverse-proxy, orchestration — la préférence self-hosted en pratique.

Demain

Le passage à un écosystème d'agents CI/CD (« Yakaframe Avancé ») : dev, test, prod et surveillance orchestrés en continu.

Fil rouge : la même idée, à trois échelles. Le développeur reste le décideur ; l'IA exécute ; le workflow garantit que ce qui sort est fiable — que l'équipe compte deux IA ou cinquante agents.

Les trois acteurs

Trois rôles, zéro chevauchement

Le développeur ne délègue pas la réflexion — il délègue l'exécution. Chacun des trois acteurs fait son travail, jamais celui des autres.

1 · Le développeur (Stéphane) — le décideur

Il tranche sur l'architecture, valide les choix techniques et juge le résultat.

  • Définit les features et leur priorité (le backlog dans CLAUDE.md).
  • Valide ou corrige les propositions de Cowork.
  • Teste le résultat dans l'app réelle.
  • Donne du feedback qui sera mémorisé et appliqué aux sessions suivantes.

2 · Cowork (Claude — mode réflexion) — architecte & rédacteur

Cowork ne touche jamais au code. Il analyse (lecture seule), propose, documente et produit les fichiers d'instructions que Claude Code consommera.

  • Analyse le code existant pour comprendre l'état réel du projet.
  • Discute les choix techniques avec le développeur.
  • Rédige des instructions précises dans specs/instructions/.
  • Produit specs, docs projet, rapports et workflows d'outillage.

Règle absolue : Cowork ne modifie jamais le code source. Le jour où l'agent qui réfléchit est aussi celui qui exécute, il n'y a plus de contrôle.

3 · Claude Code (Claude — mode exécution) — le développeur IA

Il lit les instructions, écrit le code, lance les commandes, produit les fichiers — dans le projet réel (src/, src-tauri/, auth-api/…).

  • Lit l'instruction correspondante avant chaque tâche.
  • Implémente feature par feature, étape par étape.
  • Exécute builds, tests, linting.
  • Commite en conventional commits, avec des permissions explicites dans .claude/settings.local.json.

Préférences confirmées (transverses aux projets)

  • Réponses en français, concises et directes.
  • MVP d'abord, puis on itère. Pas de sur-ingénierie.
  • Self-hosted / open-source d'abord ; le cloud n'est qu'un fallback justifié.
  • Environnement Windows + Docker Desktop + PowerShell.
  • Isolation Docker par projet : stack, réseau, volumes et ports hôte distincts (<projet>-dev-*).
  • Plans détaillés validés vite (souvent l'option « Recommandé ») ; commits atomiques par étape.
Le workflow en pratique

Le cycle d'une feature

Chaque feature passe par le même cycle : le développeur exprime un besoin, Cowork le traduit en instruction écrite, Claude Code implémente, le développeur juge.

  1. Le développeur exprime un besoin.
  2. Cowork analyse le code existant (lecture seule).
  3. Discussion développeur ↔ Cowork (choix techniques, arbitrages, scope).
  4. Cowork rédige un fichier d'instructions → specs/instructions/{feature}.md.
  5. Le développeur valide les instructions.
  6. Claude Code lit et implémente (étape par étape, commits intermédiaires).
  7. Le développeur teste et donne du feedback.
  8. Si correction nécessaire → retour à l'étape 2, en Cowork.

Le cycle de correction d'erreur

Quand Claude Code prend une mauvaise direction, le développeur ne corrige pas l'IA ligne par ligne. Il remonte au niveau de la décision (en Cowork), et la décision redescend sous forme d'instruction écrite.

Constat
Le développeur voit le problème
→
Cowork
Diagnostic & solution
→
Instruction
fix-{problème}.md → Claude Code applique

Pourquoi écrire l'instruction ? La mémoire de l'IA est volatile ; les fichiers d'instructions sont permanents. Six mois plus tard, l'historique des décisions est toujours là — relisible par l'IA comme par l'humain.

La qualité par le workflow

Quatre piliers ferment la boucle

1 · Séparation réflexion / exécution

Une IA qui réfléchit et code en même temps optimise localement. En séparant les rôles, chaque décision passe par un filtre : est-ce cohérent avec le reste du projet ?

2 · Instructions écrites = specs vérifiables

Pas un prompt vague : le problème, l'existant, la décision, les étapes, les fichiers, les comportements attendus. Documentation vivante, écrite avant l'implémentation.

3 · Vérification automatique

L'IA génère le code, les outils le vérifient, le développeur juge. Aucun des trois ne fait le travail des deux autres.

4 · Feedback persistant

Chaque correction et préférence est mémorisée (mémoire projet Claude) et appliquée aux sessions suivantes. L'IA apprend de ses erreurs si — et seulement si — le workflow le prévoit.

Cas réel (IAKA Vod) : Claude Code voulait ajouter FFmpeg pour le transcodage vidéo. C'est en Cowork que la décision a été prise de l'abandonner — les players natifs (AVPlay, Shaka, hls.js) décodent tout en hardware. Claude Code seul aurait implémenté une solution complexe et inutile.

Ce que cette méthode n'est pas

  • Pas du « vibe coding ». Pas de prompt vague suivi d'une acceptation aveugle.
  • Pas de l'automatisation aveugle. Chaque cycle passe par le développeur ; le feedback humain est structurel.
  • Pas un remplacement du développeur. Il fait moins de frappe et plus de décisions ; le métier monte en abstraction.
Infrastructure — homelab iakabox

L'infra auto-hébergée qui porte la méthode

La préférence self-hosted n'est pas théorique : iakabox est un homelab multi-VM sur le LAN 192.168.2.0/24 qui héberge Git, l'IA locale, le reverse-proxy et l'orchestration.

Git par défaut : Forgejo

Tout projet est versionné sur le Forgejo auto-hébergé. Pattern : http://192.168.2.11:3001/sjupin/<repo>.git, en HTTP + token (le SSH de cette box est inutilisable). Le token n'est jamais commité (variable $env:FORGEJO_TOKEN). Création de dépôt via l'API (description ASCII uniquement, sinon HTTP 422).

IA locale — VM3 (GPU RTX 3060)

La VM3 expose toute l'IA locale, backend idéal pour les apps de la méthode.

Horizon — « Yakaframe Avancé »

De l'équipe augmentée à l'écosystème d'agents

La même méthode, poussée à l'échelle : passer d'une équipe de deux IA pilotées à la main à une chaîne CI/CD entièrement automatisée par des agents spécialisés, fonctionnant « au fil de l'eau ».

Le sprint qui ne dort jamais

La méthode ne remplace pas l'agilité — elle l'accélère, en comprimant ce qui prenait des jours en heures, sans sacrifier la rigueur.

Sprint classique

Ticket, daily, 2-3 jours de code, PR, attente de review, corrections, merge. Une feature = 1 à 2 semaines.

Sprint IA-augmenté

Le besoin est exprimé, Cowork rédige l'instruction en minutes, Claude Code implémente en continu, le développeur review et itère. Une feature = quelques heures à 1-2 jours.

Le cœur de la cible : une chaîne d'intégration et de déploiement continus, entièrement automatisée par des agents spécialisés.

Incarnation — l'équipe iakaframe

Sept agents, un rôle chacun

L'écosystème « Yakaframe Avancé » prend corps : chaque rôle de la chaîne CI/CD est incarné par un agent nommé, au périmètre fermé. Les trois acteurs restent le modèle ; l'équipe en est la spécialisation industrielle.

L'image est mutualisée, le conteneur est étanche.

Comme l'isolation Docker par projet, on sépare définition et exécution : une persona est définie une seule fois et réutilisée partout, mais chaque projet instancie sa propre équipe, scopée à son repo. Aucun agent ne porte deux projets dans un même contexte — la répartition entre projets est un choix de portefeuille, pas un comportement d'agent.

Les jalons — qui fait quoi

Une feature avance par jalons. À chaque jalon, un seul agent est aux commandes ; Aragorn enchaîne et vérifie le gate avant de passer au suivant.

Subagents dispatchables

Chaque agent = un subagent Claude Code (agents/<nom>.md) à contexte isolé, dispatchable par Aragorn et parallélisable (N Gimli en worktrees).

Skills = savoir-faire

Le rôle charge une skill (skills/iakaframe-*). Le subagent est le contrat ; la skill est la méthode. Déclinable Claude / ChatGPT / IA locale.

Aragorn ↔ toi sur Slack

Communication bidirectionnelle via n8n (qui porte les secrets) : Aragorn poste jalons, blocages et demandes de feu vert, et lit tes réponses — arbitrages, ordres de dispatch, feu vert prod. Un canal de pilotage à distance. self-hosted : Mattermost

Tout agent peut solliciter Stéphane directement ; Aragorn est l'interlocuteur par défaut. À l'inverse, Stéphane peut demander à Aragorn de lancer un travail sur un agent (ordre de mission + dispatch, après vérification du gate amont). Aucun agent ne franchit seul un gate de production.

Commandes & cycle de vie

Deux commandes pour toute la vie du projet

La méthode s'amorce et se maintient en deux gestes, sur un projet neuf comme existant.

« init iakaframe »

Sur un répertoire vide : nouveau projet (dépôt Forgejo, structure, premier commit, état des lieux v0.1.0). Sur un répertoire avec du code : reprise — structure déployée autour de l'existant, rien d'écrasé.

Orchestrateur : iakaframe-onboard.ps1 (init + forgejo + commit + snapshot).

« update iakaframe »

Le checkpoint en une fois (iakaframe-update.ps1) : régénère l'état des lieux, puis git add -A + commit global + push. À chaque changement de version et à chaque pause/reprise (-Reason version|pause|reprise).

Auto-détection init ↔ update : les deux commandes interrogent l'API Forgejo. init sur un dépôt déjà présent bascule en update ; update sur un dépôt absent bascule en init. Une seule chose à retenir — le bon comportement est choisi tout seul.

L'état des lieux, régénéré aux bons moments

iakaframe-snapshot.ps1 produit specs/etat-des-lieux.md + .html à partir des faits git (version, branche, derniers commits, arbre propre/sale) et tient un journal append-only. Les faits sont automatiques ; Cowork complète le récit de reprise. Reprendre un projet = lire l'état des lieux, pas fouiller sa mémoire.

Gérer et lancer l'équipe d'agents

iakaframe-agents.ps1 gère les agents et les affecte aux projets. La full team se déploie en une commande — chaque projet reçoit sa copie scopée (subagents + skills + catalogue de chartes).

CommandeEffet
-Action listliste les agents canon + leur skill
-Action create -Agent <nom>scaffold un nouvel agent depuis le template
-Action affect -Agent <nom> -Project <p>affecte un agent à un projet
-Action fullteam -Project <p>déploie la full team dans un projet
-Action status -Project <p>liste les agents déjà affectés
 
# déployer toute l'équipe dans un projet
pwsh iakaframe-agents.ps1 -Action fullteam -Project C:\work\monprojet
