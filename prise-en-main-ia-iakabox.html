Le point de départ

Une iakabox, c'est un petit cloud privé posé chez toi. À l'intérieur, une machine équipée d'une carte graphique fait tourner des modèles d'IA en local. Tu n'as rien à installer côté serveur : tout est déjà là, il faut juste savoir s'y brancher.

Tu viens de ChatGPT Pro + Codex. Tu as donc déjà les bons réflexes : un chat pour réfléchir, un agent de code (Codex) pour exécuter. La box te redonne exactement ces deux usages, mais en local : tes prompts et ton code ne sortent plus de chez toi, et il n'y a plus de compteur de tokens à la fin du mois.

Comprendre l'architecture

App, Runner, Modèle : les 3 couches de l'IA

Une « IA » n'est pas un bloc unique : ce sont trois couches empilées et indépendantes. Comprendre où passe la frontière explique pourquoi on peut changer de modèle sans changer d'app, mélanger plusieurs modèles dans une équipe, ou brancher Codex sur ta box.

🧠

Le MODÈLE — le cerveau, mais inerte

Un gros fichier de « poids » (plusieurs Go) : qwen2.5, mistral, llama3.1, qwen2.5-coder… C'est le savoir figé, le résultat de l'entraînement. Seul, il ne fait rien — c'est un disque vinyle posé sur une étagère.

⚙️

Le RUNNER — le moteur qui fait tourner le modèle

Le programme qui charge le modèle en mémoire (GPU), le fait « réfléchir » et expose une API pour lui parler. Sur ta box, c'est Ollama. C'est la platine vinyle : elle lit n'importe quel disque et en sort un signal. Autres runners du monde : llama.cpp, vLLM, LM Studio.

🖥️

L'APP — ce que toi, humain, tu touches

L'interface ou l'outil qui envoie tes demandes au runner et t'affiche les réponses. Open WebUI (chat web), un agent de code comme Codex ou Aider, AnythingLLM (tes docs)… C'est la chaîne hi-fi et les enceintes : tu changes d'ampli sans changer de platine ni de disque.

Ce que ce découpage permet

Les trois couches sont interchangeables indépendamment :

  • Changer de modèle sans toucher à l'app — dans Open WebUI, un menu déroulant te fait passer de mistral à qwen2.5-coder. Même app, autre cerveau.
  • Garder ton app préférée, changer de moteur — Codex parle « API OpenAI ». Si on fait répondre la box dans ce langage, Codex ne voit pas la différence et tape sur ta box au lieu du cloud.
  • Mélanger les modèles — rien n'oblige une équipe d'agents à utiliser le même cerveau partout (on y revient en onglet 4).

L'« API compatible OpenAI ». La plupart des outils IA savent parler le dialecte d'OpenAI ; Ollama en parle un un peu différent. LiteLLM (sur ta box, port 4001) sert de traducteur : il présente une API OpenAI standard et la traduit vers Ollama. En pratique, un outil prévu pour ChatGPT peut être branché sur ta box en changeant deux réglages : l'adresse et la clé.

Piège à connaître : abonnement ChatGPT ≠ clé API. Toutes les apps (Open WebUI, AnythingLLM, Codex, Aider…) se branchent sur la couche API — jamais sur ton compte grand public. Or chez OpenAI ce sont deux produits distincts, deux factures : l'abonnement ChatGPT (le site chatgpt.com, forfait fixe) n'inclut aucun accès API, tandis que la clé API (platform.openai.com) se paie au token, à part. Conclusion : tu ne peux pas « connecter ton abo ChatGPT Pro » dans Open WebUI ni dans AnythingLLM. Trois choix réalistes : ① les modèles locaux de la box (gratuit, privé — le défaut conseillé) ; ② une vraie clé API OpenAI (qualité GPT, mais coût en plus de l'abo) ; ③ surtout pas les ponts « ChatGPT web → API » non officiels (contraires aux CGU, risque de bannissement).

Quatre parcours, du plus simple au plus complet. Chacun est autonome : prends celui dont tu as besoin.

Scénario B — Le chat web (Open WebUI) quotidien

Objectif : une interface proche de ChatGPT — historique, choix du modèle, fichiers joints — sans rien installer.

  2. Crée ton compte (le premier compte créé est en général l'administrateur — demande à ton installateur si c'est déjà pris).
  3. En haut de la conversation, déroule la liste des modèles et choisis-en un (ex. qwen2.5 pour discuter, qwen2.5-coder pour du code).

Scénario C — Remplacer Codex par un agent de code local avancé

Objectif : retrouver un agent qui lit ton dépôt, modifie les fichiers et lance les commandes, mais branché sur ta box. Principe (cf. onglet 2) : on pointe l'agent sur LiteLLM, qui parle le langage d'OpenAI.

  1. Assure-toi qu'un bon modèle de code est présent (voir encadré ci-dessous) — par ex. qwen2.5-coder:7b.
  2. Dis à l'agent « ton OpenAI, c'est ma box ». La plupart des agents (dont Codex) lisent deux variables d'environnement : 
    # L'adresse de l'API : on vise LiteLLM sur la box, pas le cloud OpenAI
export OPENAI_BASE_URL=http://192.168.2.12:4001
# Une clé est exigée par le protocole, mais en local elle peut être bidon
export OPENAI_API_KEY=sk-local-peu-importe
  3. Lance ton agent dans le dossier de ton projet. Exemple avec Aider (agent de code open-source, qui fonctionne bien avec les modèles locaux) : 
    pip install aider-install && aider-install   # une fois
cd mon-projet
aider --model openai/qwen2.5-coder:7b      # via le câble OpenAI ci-dessus
  4. Demande-lui une tâche concrète : « ajoute une route /health qui renvoie OK ». Il propose un diff, tu valides, il écrit. Comme Codex.

Quel agent choisir ? Tu peux garder Codex lui-même (il accepte une base URL personnalisée), ou passer à un agent pensé pour le local : Aider (CLI), ou des extensions d'éditeur comme Continue / Cline dans VS Code. Tous suivent la même logique : adresse = ta box, clé = peu importe. Claude Code (l'outil utilisé pour produire ce guide) reste une option pour les sessions nécessitant un agent cloud.

Limites du matériel. Un modèle local de 7–14 milliards de paramètres traite bien des tâches de code cadrées, mais n'égale pas les meilleurs modèles cloud sur un gros raisonnement d'architecture. Approche raisonnable : local pour le quotidien (boilerplate, refactor, tests, petites features), cloud pour les cas les plus difficiles. Le découpage App/Runner/Modèle permet justement de changer de modèle selon le besoin.

La marche d'après

D'un chat unique à une équipe d'agents spécialisés

Une fois à l'aise avec le chat et l'agent de code, une question arrive vite : pourquoi un seul agent généraliste, qui code et se relit et teste tout seul ? Dans la vraie vie, un dev seul qui valide son propre travail laisse passer des erreurs. Une équipe, avec des rôles séparés, en laisse beaucoup moins. C'est l'idée de la méthode iakaframe.

Pourquoi spécialiser plutôt qu'un gros prompt fourre-tout

  • Un rôle = une mission claire. Un agent « architecte » qui conçoit, un agent « codeur » qui exécute, un agent « relecteur » qui critique, un agent « testeur/qualité » qui valide. Chacun fait une chose et la fait bien.
  • Personne ne valide son propre code. Le relecteur n'est pas le codeur. Les contrôles (« portes ») sont indépendants : c'est ce qui attrape les bugs qu'un agent unique s'auto-pardonne.
  • Des prompts plus courts et plus nets. Un agent spécialisé a un contexte étroit → il dérive moins, il est plus rapide, il coûte moins.

iakaframe en une phrase. Trois acteurs, zéro chevauchement : toi = décideur (vision, arbitrages, validation) ; un Claude « réflexion » qui écrit les instructions mais ne touche pas au code ; un Claude « exécution » qui lit l'instruction, code, build, teste, commite. Le cycle d'une feature : besoin → analyse → discussion → instruction écrite → validation → implémentation → test → on recommence.

Le multi-modèle : le bon cerveau pour chaque rôle

C'est une application directe du cours de l'onglet 2. Puisque l'app et le modèle sont découplés, rien n'oblige tous les agents à partager le même modèle. On affecte le modèle au rôle :

Rôle de l'agentType de modèlePourquoi
Architecte / relecteurgros & malin (qwen2.5-coder:14b, ou un modèle cloud)Raisonnement, vision d'ensemble, détection de pièges
Codeurspécialisé code (qwen2.5-coder:7b)Bon rapport qualité/vitesse sur l'écriture de code
Tâches mécaniquespetit & rapide (llama3.2:3b)Renommer, reformater, résumer : un petit modèle suffit

Tu places ainsi la puissance (et le coût) sur les rôles qui en ont besoin, et tu gardes du débit sur les tâches triviales. Une équipe de modèles adaptés au rôle est généralement plus efficace qu'un modèle unique appliqué à tout.

Les jalons : avancer par paliers vérifiés

Un jalon (milestone), c'est un point d'étape où on s'arrête pour valider avant de continuer. Plutôt que laisser l'IA travailler longtemps et découvrir les problèmes à la fin, on cadence :

  1. Instruction écrite et validée par toi → l'agent sait exactement quoi faire.
  2. Implémentation d'un morceau cohérent et petit.
  3. Porte de qualité : build + lint + tests passent (sinon on ne franchit pas le jalon).
  4. Commit atomique → un point de sauvegarde propre.
  5. Ton feedback réel → on ajuste, puis jalon suivant.

Utile même seul. Même avec un seul agent de code, suivre ces 5 étapes par petits incréments te garde le contrôle, et tout écart reste rattrapable au dernier commit.

Le filet de sécurité

Commits, CI, et tests Docker en parallèle

Quand une IA modifie ton code, trois pratiques limitent fortement les dégâts et permettent de revenir en arrière : les commits fréquents, la CI, et les tests isolés sous Docker. Ta box héberge déjà le git (Forgejo) qui rend tout ça accessible.

1. Les commits : revenir en arrière à tout moment

Un commit, c'est une photo de ton projet à un instant T. La règle : petits et fréquents (un par jalon). Avantages quand une IA travaille :

  • Retour arrière immédiat si une modif part de travers — tu reviens au dernier bon commit.
  • Historique lisible de qui a fait quoi (messages en « conventional commits » : feat:, fix:, test:…).
  • Jamais de git reset --hard ni de push --force par l'IA — règle d'or : l'IA n'efface pas l'historique.

2. La CI : un robot qui vérifie à chaque commit

La CI (intégration continue), c'est une recette automatique qui, à chaque commit poussé, refait les vérifications : installer, build, lint, tests. Si quelque chose casse, tu le sais tout de suite — pas trois jours plus tard.

Sur ta box. Forgejo (le git de l'iakabox) sait lancer des « Actions » à chaque push, comme GitHub. La CI peut tourner les tests dans un conteneur Docker propre, à chaque fois identique. Tu n'as à l'écrire qu'une fois.

3. Les tests sous Docker : pareils partout, jetables

Lancer les tests « sur ta machine », c'est dépendre de ta version de Node, tes variables, tes bibliothèques. Docker enferme le projet dans une boîte reproductible : même résultat sur ton poste, sur la box, dans la CI. Et à la fin, la boîte se jette — aucune pollution.

Convention iakaframe : chaque projet a sa propre stack Docker (réseau, volumes, conteneurs préfixés par le nom du projet) et ses propres ports. Aucun projet ne marche sur les pieds d'un autre.

4. Plusieurs versions en parallèle — le cas du dev web

Particulièrement utile en dev web. Pour comparer deux pistes (l'existant et la proposition de l'IA), ou tester une branche sans casser ce qui marche, tu lances plusieurs versions en même temps, chacune dans sa boîte Docker, sur un port différent :

# Version actuelle (référence) sur le port 8080
docker compose -p monsite-main up -d        # http://localhost:8080

# Version proposée par l'IA sur le port 8081, en parallèle
docker compose -p monsite-ia up -d          # http://localhost:8081

Tu ouvres les deux onglets côte à côte, tu compares directement dans le navigateur, tu gardes la version retenue et tu supprimes l'autre. Le -p <nom> isole chaque version (réseau + conteneurs distincts) ; les ports distincts évitent les collisions.

Le rituel complet, bout à bout. L'agent code une feature (jalon) → la CI build + lint + teste sous Docker → tu lances la nouvelle version sur un port à part → tu la compares à la version de référence dans le navigateur → si c'est bon, commit + merge ; sinon, retour arrière, et l'instruction est affinée. C'est le cycle iakaframe complet.

Pour qui code avec Codex

Installer iakaframe dans Codex CLI

Tu gardes Codex comme agent d'exécution et tu ajoutes par-dessus le cadre iakaframe. La méthode est identique à l'incarnation Claude ; seules deux choses changent : le contrat s'appelle AGENTS.md (au lieu de CLAUDE.md) et les agents deviennent des personas — tu joues un rôle à la fois, annoncé explicitement.

Le kit existe déjà. iakaframe fournit un kit Codex dédié : kit-codex/ (un AGENTS.md + des gabarits specs/). Tu n'écris pas le contrat toi-même, tu le déposes à la racine du repo.

Pré-requis

  • Codex CLI installé et connecté à ton compte ChatGPT (ou ta clé API).
  • Git sur ton poste, et un dépôt pour ton projet (le Forgejo de la box fait un remote idéal, mais un repo local suffit pour commencer).
  • Le dossier kit-codex/ d'iakaframe (demande-le à l'utilisateur, ou récupère-le depuis le Forgejo).

Pas à pas

  1. Place-toi dans ton projet (ou crée-le) : 
    mkdir mon-projet && cd mon-projet
git init
  2. Dépose le contrat et les gabarits à la racine du repo. Copie le contenu de kit-codex/ : 
    # tu dois obtenir, à la racine :
AGENTS.md                      # le contrat, lu auto par Codex
specs/PROJET.md                # vision / décisions
specs/instructions/_TEMPLATE.md # gabarit d'instruction
  3. Remplis la vision dans specs/PROJET.md (stack, objectif, contraintes). Jamais de code ici.
  4. Lance Codex dans le dossier. Il lit AGENTS.md automatiquement à chaque session — il connaît désormais la méthode, les rôles et les règles. 
    codex            # Codex charge AGENTS.md (= ton contrat iakaframe)
  5. Phase 1 — Cadrage (persona 🧙 Gandalf). Demande à Codex d'endosser Gandalf et d'écrire l'instruction de ta 1ʳᵉ feature dans specs/instructions/<feature>.md. Tu la valides avant tout code.
  6. Phase 2 — Réalisation (persona ⚒️ Gimli + 🏹 Legolas). Instruction validée → Codex implémente par étapes, lance typecheck + lint + tests, et commite en conventional commits.
  7. Jalon : régénère l'état des lieux puis commit/push avec les scripts iakaframe (agnostiques de l'agent) : 
    pwsh iakaframe-snapshot.ps1 -Reason pause
pwsh iakaframe-update.ps1            # commit global + push Forgejo
  8. Boucle : feature suivante → retour à l'étape 5. La chaîne s'arrête au staging ; la mise en prod est un squad séparé (🌉 Helm) sur ton feu vert.

Différence clé avec Claude. Chez Claude, les rôles sont des sous-agents dispatchables. Sous Codex, ce sont des personas joués en série : « je suis Gandalf, je cadre » puis « je suis Gimli, j'implémente ». Le gate « ne pas valider son propre code » se tient via une passe de revue distincte (persona Legolas, sur le diff seul) + la CI Forgejo comme juge objectif.

Faire tourner certains personas sur Ollama (multi-modèle dans Codex)

Oui, c'est possible, grâce au découpage App/Runner/Modèle (onglet 2). Codex sait viser un fournisseur personnalisé compatible OpenAI : on pointe sur LiteLLM de la box (192.168.2.12:4001), puis on crée un profil par persona. Comme tu joues un rôle à la fois, tu choisis le modèle à l'invocation.

# ~/.codex/config.toml

# 1) Déclarer la box comme fournisseur "façon OpenAI" (via LiteLLM)
[model_providers.iakabox]
name = "iakabox (LiteLLM -> Ollama)"
base_url = "http://192.168.2.12:4001/v1"
env_key = "IAKABOX_API_KEY"   # clé bidon en local, mais exigée par le protocole

# 2) Un profil par persona : modèle + fournisseur
[profiles.gandalf]                 # cadrage/archi : raisonnement -> cloud (ton abo)
model = "gpt-5"                  # mets l'id exact dispo dans ton Codex

[profiles.gimli]                   # dev : code -> LOCAL sur la box
model = "qwen2.5-coder:7b"
model_provider = "iakabox"

[profiles.legolas]                 # revue/qualité : un AUTRE modèle que Gimli
model = "qwen2.5-coder:14b"
model_provider = "iakabox"
export IAKABOX_API_KEY=sk-local-peu-importe    # PowerShell : $env:IAKABOX_API_KEY="..."
codex --profile gimli      # je joue Gimli, sur le modèle LOCAL de la box
codex --profile gandalf    # je joue Gandalf, sur le cloud de ton abo

Vérifie la syntaxe selon ta version de Codex (codex --help / sa doc de config) : les clés model_providers / profiles / base_url / env_key peuvent légèrement varier. Le principe ne change pas : fournisseur = la box, profil = persona.

En pratique. Cadrage et revue (Gandalf, Legolas), où le raisonnement compte → cloud ou gros modèle. Écriture de code en volume (Gimli) → local sur la box, gratuit et privé. La puissance — et le coût — sont placés sur les rôles qui en ont besoin.
