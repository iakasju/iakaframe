Et Gimli ?

⚒️ Gimli (développement + devops, P2 → P3) n'a pas de skill dédiée : son cadre vit dans le CLAUDE.md du projet et l'outillage. En faire une skill la ferait sous-déclencher.

Zoom

Quatre briques clés, de plus près

Au-delà du cœur du cycle, ces quatre skills couvrent des trous réels de la méthode déjà décrits dans methode-de-travail.md ou dans la charte — pas une invention, une formalisation.

iakaframe-forgejo nouveau

Le dépôt git par défaut de tout projet vit sur le Forgejo auto-hébergé d'iakabox (HTTP + token, création via API, description ASCII, auto-détection d'existence).

Le manque : ce composant est déjà nommé dans la méthode (l'orchestrateur d'amorçage = init + forgejo + commit + snapshot) mais n'existait pas comme skill. C'est la brique la plus casse-gueule (token, 422 sur desc non-ASCII, SSH inutilisable).

iakaframe-docker nouveau

La convention isolation Docker par projet : stack propre, containers <projet>-dev-*, réseau et volumes dédiés, ports hôte décalés pour ne jamais entrer en collision (ex. 5432 / 5433 / 5434).

Le manque : allouer des ports sans collision et préfixer toute la stack est multi-étapes et facile à rater. Un cadre explicite évite que deux projets de la famille se marchent dessus.

iakaframe-update nouveau

La commande « update iakaframe » : régénère l'état des lieux, fait un commit global atomique et pousse.

Le manque : etat-des-lieux est en lecture seule (il constate). Il manquait sa contrepartie en écriture qui grave le point de sauvegarde. Symétrie naturelle : l'une lit, l'autre commite.

iakaframe-naonedge nouveau

Produire un support on-brand (doc, deck, flyer) selon la charte NaonEdge — dark premium · or — sans diverger de design-naonedge/.

Le manque : « écrire une doc en style NaonEdge » est exactement le genre de tâche multi-étapes que la charte rend reproductible. Cette page en est la première application.

Le principe

Une skill par rôle d'agent — et les exceptions

Une skill se justifie là où un cadre explicite change le résultat. Depuis l'équipe d'agents, chaque rôle au périmètre fermé a la sienne. Restent écartés volontairement :

Candidat écartéPourquoi pas une skill
⚒️ Gimli — développement + devops (P2 → P3)Porté par le CLAUDE.md du projet et l'outillage. En faire une skill la ferait sous-déclencher. Seul agent sans skill dédiée.
Cycle de correction d'erreurVariante de iakaframe-cadrage (instruction fix-*.md), pas un cadre distinct.
Mock des API (specs/mock/)Convention de dev appliquée dans l'exécution ; pas assez multi-étapes. À reconsidérer si le besoin grossit.

Note : la validation sur staging (P3) est couverte par iakaframe-qualite (Legolas) et la bascule en prod par iakaframe-deploiement (Charon, squad prod) et la surveillance prod par iakaframe-surveillance (Helm, squad prod) — plus des trous, donc plus des écartés.

Règle qui traverse tout —

L'IA prépare et propose à l'intérieur d'un périmètre borné ; l'humain décide aux gates. qualite matérialise le gate automatique, deploiement le gate humain. Aucune skill ne franchit seule un gate de mise en production.

Installation

Déposer les skills

Chaque dossier iakaframe-* contenant un SKILL.md se dépose dans le répertoire de skills ; il se déclenche automatiquement quand le contexte correspond à sa description.

# Claude Code — global ou projet
~/.claude/skills/iakaframe-*        # pour toutes les sessions
.claude/skills/iakaframe-*          # pour ce projet seulement

# Cowork — via le panneau des skills
